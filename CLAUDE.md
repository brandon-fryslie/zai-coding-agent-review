# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A GitHub Action that runs an AI coding agent as a code reviewer. The engine is chosen by the `PROVIDER` input in `src/provider.js`, which defaults to `auto` — the action's own choice, today Claude Code against Anthropic on a Claude Pro/Max **subscription** (`CLAUDE_CODE_OAUTH_TOKEN`), retargeted from DeepSeek in 1.42.0. It can also run the Codex engine against OpenAI (`PROVIDER: codex`) or Claude Code against Z.ai (`PROVIDER: zai`). Whichever engine runs, it records required changes through a private MCP "collector" tool.

**Two review modes, selected by the `MODE` input (`src/run.js`).** `MODE` is the explicit discriminator between two *materials* and two *sinks*:
- **`pr`** (default) — review a pull request diff and submit an inline `REQUEST_CHANGES`/`APPROVE` GitHub review (`runPrReview`).
- **`repo`** — an on-demand whole-repo review (typically `workflow_dispatch`) with an optional free-text `SCOPE` injected into the prompt; the engine explores the working tree with Read/Grep/Glob (no diff, no anchors), and findings are printed as a Markdown report to the GitHub Step Summary + run log — no PR, no host review, no GitHub write token (`runRepoReview`). Pre-existing issues are in scope here, the inverse of PR mode.

**Every review is one adaptive multi-scope pass** (`runMultiScope` in `src/multiscope.js`), shared whole by both modes: a **scout** plans review scopes, one **worker** reviews each scope, and the workers' findings + usage **aggregate** into a single review value. The worker layer then re-runs as **convergence sweeps** over the same scopes — each sweep's prompt carries the findings already recorded and hunts only for what is missing — until a sweep adds nothing new (by the `dedupeFindings` key) or the effort profile's `sweepCap` (`src/effort.js`, priced in `src/budget.js`) is reached, so one round front-loads what push-triggered rounds used to dribble out. Adaptivity is the grouping, never a counted threshold — the scout groups the change by concern (folding boundary review *into* each concern's scope), so scope count equals the number of concerns the change touches: a one-concern change yields one scope, a multi-concern change yields several, a whole-repo audit yields one scope per concern. [LAW:dataflow-not-control-flow] The whole pass is **one `produceReview` attempt per config** (`src/failover.js`), so retry/failover and cost-summing (`sumUsage`) wrap the entire scout→workers pass as a unit.

**The run owns a wall-clock budget** (`src/deadline.js`, zai-timing-sn1): `run()` mints ONE absolute deadline from `TIME_BUDGET_MINUTES` (default 25, `0` = off) and threads it down as a value. Every engine spawn is bounded by `min(adapter cap, time remaining)` — a deadline kill is a typed `DeadlineExceededError`, distinct from the adapter-cap timeout — and the multi-scope scheduler stops *starting* workers and sweeps once the budget is spent. The worker pool absorbs a deadline kill as a per-scope `unreviewed` outcome (pass 0 = a coverage gap named in the summary and carried as `unreviewedScopes`; a sweep = merely curtailed convergence), so completed scopes' findings are always SUBMITTED; a partial review's verdict withholds approval (`PARTIAL_MESSAGE`, event `COMMENT`) while blocking findings still `REQUEST_CHANGES`. The time budget is one of **two** coverage gaps that withhold approval; the other is a changed file refused at the diff boundary (`parseReviewableFiles`, below). `submitReview` requires both as fields of the review value (`unreviewedScopes`, `unreviewableFiles`) and derives approvability from them in ONE expression, so a new gap is added to that conjunction and nowhere else. [LAW:single-enforcer] Only a budget that expires before ANY scope completes fails the run — loudly, naming the knob. This exists because the workflow's `timeout-minutes` cancel discards every collected finding; the budget makes the action finish and deliver *before* that kill can fire. [LAW:no-ambient-temporal-coupling] A kill signals the engine's whole **process group** (SIGTERM, then SIGKILL after `adapter.killGraceMs`) and settles only on `'close'` — when the tree has actually exited and released the stdio pipes — so temp-dir cleanup can never race a dying engine (the live ENOTEMPTY crash) and an orphaned grandchild can never outlive the run; scratch-dir removal failures warn (`removeQuietly`) rather than outrank the review result.

The scout records each scope through the **`add_scope` collector tool** — a typed, schema-validated record (`parseScopeValue` in `src/review.js`), exactly as a worker records a finding through `request_change` or a per-module dependency judgment through `assess_dependency` (`parseAssessmentValue`). The plan is never parsed from the model's prose; the tool schema *is* the type (`[FRAMING:representation]`). `readCollectedReview` returns `{summary, findings, scopes, assessments}` — one reader, three record kinds: a scout run yields scopes, a worker run yields findings (and, for the worker that owns a bumped `go.mod`, dependency assessments), all through the same exactly-one-`finish_review` gate.

The two modes share this entire engine plus `buildConfigChain` and the cost machinery. They differ only in the *material* (what the scout surveys + what each worker reviews — `buildPrMaterial` over an annotated diff vs `buildRepoMaterial` over the working tree, built from `buildPrScoutInput`/`buildRepoScoutInput` + `buildReviewInput`/`buildRepoReviewInput` in `src/prompt.js`) and the *sink* (`submitReview` in `src/transport.js` vs `renderRepoReport` in `src/report.js`). The PR-diff anchor machinery (`patchLines`/`buildReviewAnchors`/`partitionFindings`) is a `pr`-mode-only concern, applied once in the PR sink to the merged findings; in `repo` mode any `file:line` the agent cites is valid. The local diagnostic `scripts/local-review.js` drives this same `runMultiScope` for **both** modes (material is the only differential), so neither mode can be exercised in production but not locally.

**The reviewer is told what was taken out of its view.** `EXCLUDE_PATTERNS` removes changed files from the reviewed diff, and for a model handed the survivors, absence-by-configuration is indistinguishable from absence-by-omission: it reasons about "the diff" while holding a SUBSET of it and reports the gap as a defect. On PR #117 that produced a confident, release-blocking "`dist/` was never rebuilt" against a PR that rebuilt it in every commit — a natural experiment confirmed it, since the same engine over the same delta with no exclusions read `dist/index.js` and reported the bundle matched. Every finding blocks, so a false one costs a human adjudication. [LAW:no-silent-failure] The fix is a value, not a prompt rule: `filterFiles` (`src/diff.js`) returns the SPLIT — `{reviewed, excluded: {patterns, paths}}` — so the record of what was hidden is made where it is known and rides to `buildPrMaterial` as one field, reaching both the scout prompt ("never scope an invisible path") and every worker and sweep prompt ("absent by configuration, not by evidence — never record a finding asserting one was missed"). Re-globbing the patterns in `src/prompt.js` would be a second, drifting answer to "what did we hide?", and recovering the count by subtracting list lengths — what `run.js` used to do for its log line — is the same lie in lossy form. [LAW:one-source-of-truth] The note names the withheld **paths** — not just the patterns — because naming only the patterns MEASURABLY LOST: delivered verbatim to all 15 engine spawns of a real run (grepped from that run's own transcripts), it still drew the same `[S4]` "`dist/` was not rebuilt" on a PR whose `dist/` matched a fresh build byte-for-byte. A predicate about an unseen file asks the model to notice an absence, recall the globs, test a name it was never shown, and then retract a conclusion it has already evidenced — from *this repo's own* `check-version-bump.sh` and the `dist/` rule above. Naming the file as changed-and-withheld deletes the premise instead of arguing with the conclusion; the clause conceding a read repo rule while denying that this material can witness compliance **either way** closes the escape route the model actually took. [FRAMING:representation] The list is rendered by `excludedPathList` (`src/diff.js`, beside the record it renders) — the ONE way a withheld set is displayed at every sink: the scout prompt, every worker and sweep prompt, the operator log, and the plan boundary's warning. It is bounded (`MAX_EXCLUDED_PATHS_SHOWN`, 20) with an honest "(and N more)" tail, since in a prompt it is paid on every spawn and a vendored-tree bump would otherwise inflate all of them — and one unbounded operator log line floods the Actions log while telling nobody more than a bounded one does. A truncated list that lied about its own length would be the same withheld-information defect one level down; two sinks rendering the same set their own way would be two truncation contracts. [LAW:one-source-of-truth] Patterns that matched nothing hid nothing, so the material stays byte-identical to an unconfigured run.

**Telling the scout those paths is what makes it able to avoid them, and the only reason it could ever name one** — so the prompt sentence is the request and `planScopes` (`src/multiscope.js`) is the guarantee. A withheld path surviving into a scope reaches `buildReviewInput`'s `scopeFiles` and renders as "Read the complete content of THESE files", the literal opposite of the same prompt's "Do not read these paths", resolved by whichever instruction the worker weighs harder. The plan boundary strips it instead: `withoutWithheldFiles` removes withheld paths from every scope and returns them as `withheldAssignments` — a third sibling of `sweptPaths` and `duplicatePaths`, warned about in the same shape, since a scout that keeps scoping withheld files is a signal about the prompt and never a silent correction. [LAW:no-silent-failure] The predicate is the withheld set ITSELF (`material.withheldPaths`), never "not in `changedPaths`": those are two different facts — what this review covers vs. what is out of bounds — and the complement of the first equals the second only in `pr` mode, since `buildRepoMaterial` carries `changedPaths: []` by design and a complement-based check would strip every file of every scope on every `repo` run. [FRAMING:representation] A scope emptied by the strip is DROPPED, never passed through: `buildReviewInput` reads an empty `scopeFiles` as "no assigned files" and falls back to reading every changed file in full, so an empty scope would silently undo scope-bounded reads — a cost regression wearing the shape of a safety check. The strip runs BEFORE coverage is computed, so a reviewable path orphaned by a dropped scope lands in the existing catch-all rather than needing a second coverage mechanism. [LAW:one-type-per-behavior] [LAW:dataflow-not-control-flow] This is deliberately NOT the unshowable-files note it resembles: an unshowable file is still reviewable (read it at its absolute path), an excluded one is out of bounds entirely — same absence, opposite instruction, two types. [LAW:one-type-per-behavior] `repo` mode needs none of this: there is no diff, so its prompts already carry the patterns as a "do not review these" bound on exploration.

In simple mode (no `CONFIG_FILE`), `src/provider.js` is the single seam that turns the `PROVIDER` value plus its provider-specific inputs (`OPENAI_*` / `ZAI_*` / `DEEPSEEK_*` / `CLAUDE_*`) into a typed `ReviewConfig`. A committed `.github/review-agents.yml` config file is the advanced path: when it exists it owns engine selection (incl. per-PR selection and failover chains) and the simple-mode inputs are ignored.

**A changed file that cannot be reviewed withholds approval.** `parseReviewableFiles` (`src/diff.js`) is the one boundary every changed-file list crosses (`selectTransport`), refusing any path that embeds a vertical separator — no prompt line can name it and no review comment can anchor to it. A refused path is not merely logged: the refusal record (stamped there into a single-line displayable name, so every sink can render it) rides on the transport as `transport.unreviewable`, reaches `submitReview` as `review.unreviewableFiles`, is listed on the PR under "Changed files NOT reviewed", and blocks approval exactly as an unreviewed scope does. This is why `PARTIAL_MESSAGE` names no cause — the verdict line cannot know which gap fired. [LAW:no-silent-failure]

**Fork PRs are never reviewed.** `runPrReview` fetches the PR once up front and gates on `prIsFromFork` (`src/transport.js`: head repo id ≠ base repo id, or a deleted/absent head repo) — a fork PR is skipped cleanly (logged, exit 0, no engine spawned) before any **AI** credential is read. This is unconditional with no opt-in input, so an outside contributor's PR can never spend the host's AI credits. The qualifier is load-bearing: since the skip announces itself on the PR, the path DOES read the GitHub token (`reviewOctokit`) to post that notice. What it never reads is a provider credential, and the notice body is composed wholly from values this action owns — the fork's diff reaches no model and no request.

**A run that reviewed nothing says so at the PR.** Exactly TWO paths end `runPrReview` at exit 0 without a review — the fork gate and the round cap — and both were formerly invisible at every sink a consumer reads: same green conclusion, same zero findings, same absence of a posted review as a clean review. On 2026-08-21 an automerge loop read that absence as approval and came one step from merging PR #108's never-reviewed head commit, which a later local review found 19 real findings in. [LAW:parse-dont-validate] "the workflow succeeded" and "a review was produced" were two facts collapsed into one value. `announceNotReviewed` (`src/transport.js`) is the ONE mechanism both paths use: they differ only in the notice VALUE (`{reason, message, latestArtifact, reportPostFailure, postFailureHint}`, reason drawn from the closed `NOT_REVIEWED_REASONS`), never in channel. [LAW:one-type-per-behavior] The channel is a `COMMENT` review — the same one the reviewer already uses for "✅ Approved" without an approval token — so *being skipped* still exits 0 (failing that would break a required check over a deliberate cost control), the event is never `REQUEST_CHANGES` (nothing was reviewed, so no finding justifies one), and there is no input to opt in. Being *unable to say so* is the opposite case and reds the run on the round-cap path (`reportPostFailure`, below): the notice is the primary sink, so when it cannot be posted the run conclusion is the only sink a consumer has left and must carry the distinction. A third candidate is deliberately absent: a time budget that expires before any scope completes already throws `DeadlineExceededError` and reds the run, so it is loud without a notice.

The two artifacts this action can leave on a PR are told apart by **structurally disjoint trailing markers**: a round ends with `REVIEW_MARKER`, a notice with `<!-- copirate-code-review-agent:not-reviewed:<reason> -->` (built from `NOT_REVIEWED_MARKER_PREFIX` on *both* sides — the renderer and `parseAgentArtifact`'s pattern — so a rename cannot break recognition of the notice this module itself writes). A reason is drawn from the closed, *named* enumeration `NOT_REVIEWED_REASONS` (`{FORK, ROUND_CAP}`, reached by name so a typo is `undefined` at the call site) whose values are `[a-z-]` literals — no space, no `<`, no `>` — so no reason can splice the review marker back onto the end, and a notice therefore *cannot* be counted as a review round or tallied into a cost. That is a shape `summarizePriorReviews` cannot see, not a rule it must remember. [LAW:types-are-the-program] `parseAgentArtifact` is the single reader turning a body into `{kind:'review'} | {kind:'not-reviewed', reason, body} | null` — `body` is on that arm because it, not the reason, is what the idempotency key below compares; `summarizePriorReviews` derives count/cost/the review set **and** `latestArtifact` from one pass over it, so the notice's idempotency key shares the round counter's source. [LAW:one-source-of-truth] `latestArtifact` is the artifact with the **highest review id**, never whichever the loop saw last: every other output of that function is an order-independent sum, and reading the newest off arrival order would rest page ordering on a guarantee GitHub documents and Gitea does not. [LAW:no-ambient-temporal-coupling]

The key is "my own notice is still the newest agent artifact on this PR", NOT a per-PR already-told flag: a flag would go permanently silent, whereas this speaks again once the cap is raised and a real round lands. Once-per-cause holds per run, not across concurrent runs — two racing runs can both read "no notice yet" and both post, which the workflow's `concurrency` group prevents and the README names as the precondition; deliberately undefended, because the race can only make the action speak TWICE, never fall silent.

**The fork gate runs first, from the `pr` object alone, and consults no key at all.** "A fork PR is skipped, unconditionally" is only as strong as the weakest thing that decision depends on, so no prior-review fetch may precede it — that would let a transient API failure red a run that previously could not fail. **Everything that differs between the two paths rides on the notice VALUE**, built by `forkNotice(pullNumber)` / `roundCapNotice(message, latestArtifact)` (`src/transport.js`) rather than assembled at the call sites: the reason, the message, the trust key, the severity a refused post is reported at, and the hint printed with it. That severity is a carried value for the same reason the rest are: the fork's warn-only policy ("reddening would red every fork PR forever" — a fork `pull_request` run gets no repository secrets, so no configuration fixes it) does NOT transfer to a round cap, which is only reachable on a same-repo PR where `pull-requests: write` is always grantable. Applied uniformly it produced a green run with nothing on the PR — this mechanism's own failure mode, reached from the one path it was built for — while `submitReview` already throws on the identical refusal. So `roundCapNotice` carries `core.setFailed` and `forkNotice` carries `core.warning`, and `announceNotReviewed`'s catch makes ONE unbranched call; a `reason === 'round-cap'` test inside it would be precisely the invisible argument swap these constructors exist to make unrepresentable. [LAW:dataflow-not-control-flow] `forkNotice` takes no key parameter, so the fork gate has nothing to pass and cannot be edited back into consulting one without calling `roundCapNotice` by name at the fork gate — the pairing is a fact of the type, not a convention a test has to guard. [LAW:types-are-the-program]

The fork notice's `latestArtifact` is `null` — a VALUE ("no key worth trusting — post it"), not an omission: the key is parsed out of review bodies, and on a public repo any account with READ access can post a review (push access is *not* the bar), so on a fork PR its own author can forge a `not-reviewed:fork` marker and silence the notice about their own unreviewed PR. A PR we refuse to review because we do not trust it cannot also be a PR whose reviews we trust to tell us what we said. The cost is accepted and stated: a fork notice repeats on every push. This survives the author gate below rather than being made redundant by it, and must not be "simplified" away once identity checking is in place — the fork gate runs BEFORE any prior-review fetch, so the fork path never resolves an identity or reads a marker at all, and its `null` is what keeps that true. Two independent reasons the forged marker cannot land, on the path where the beneficiary IS the untrusted outsider. The asymmetry lives at the two constructors, never as a branch inside `announceNotReviewed`. [LAW:dataflow-not-control-flow]

The key itself is the **rendered body**, not the reason: "the newest artifact already says byte-for-byte what I am about to say." Keying on the reason let a notice outlive its own content — a PR capped by `MAX_REVIEW_ROUNDS` kept that notice when a later run was capped by the budget gradient instead, so the operator read the wrong cap number and a remedy that would not have helped. An exact compare (rather than a digest in the marker) because if a host ever normalized whitespace on the round trip the action speaks TWICE — the safe direction every trade here takes.

A `createReview` the host refuses degrades to a loud `core.warning` rather than reddening the run **on the fork path, and only there** (`forkNotice`'s `reportPostFailure`; the round cap's is `core.setFailed`, above): a fork PR on a `pull_request` trigger gets a read-only token by GitHub's rule (no `permissions:` block overrides it), so failing there would red every fork PR forever. `workflow_run`, never `pull_request_target`, is the trigger to recommend — `pull_request_target` beside the Quickstart's `head.sha` checkout is the pwn-request pattern. `GITHUB_REVIEW_TOKEN` is NOT an escape hatch either, however plausible it looks: a `pull_request` event from a fork receives **no repository secrets at all** (`GITHUB_TOKEN` excepted, read-only), so the input resolves empty on exactly those runs. The unknown-reason throw is raised *outside* that `try`, so a programming error stays a red run instead of being reported as a permissions problem. [LAW:no-silent-failure]

**The reviewer never leaves a blocking review it refuses to revisit.** The round cap and a `block_merge_on_rejected_reviews` branch protection are each sound alone and had no exit between them: the cap assumes a rejection is advisory and will be revisited, the gate assumes a rejection is blocking and can be cleared by a better review. So a `REQUEST_CHANGES` posted before the cap was reached could never be superseded, and an author who fixed every finding correctly was left permanently unmergeable — deadlocked, not gated, with a hand-written dismissal API call as the only documented way out. `releaseUnrevisitableBlocks` (`src/transport.js`) is the single enforcement site: the round-cap exit announces the skip and then dismisses this action's own outstanding block, because the moment it declines to look again the block asserts a conclusion it will not re-examine. [LAW:single-enforcer] It is *not* implemented as "withhold the block on the final permitted round" — the cap can shrink *beneath* a block already posted (one round costing enough to de-rate the cap to 1 strands round 1's rejection), so only releasing at the decline covers every path in. The set it can dismiss is `summarizePriorReviews`'s marker-bearing review set, which is what makes "only ever this action's own block, never a human's" a property of the data rather than a rule the release site must remember. [LAW:types-are-the-program] The release is idempotent without a flag — a released review no longer satisfies `isOutstandingBlock` on either host, so a later push filters it out and never re-attempts it. That matters because **dismissal itself is not idempotent at either host**: a second attempt answers 422 `Can not dismiss a dismissed pull request review` on GitHub, and a closed/merged PR answers 403 on Gitea (both measured). So when a dismissal *does* fail, the review is re-read and the decision comes from its state through the same `isOutstandingBlock` — a review someone else already released satisfies the goal by other means and is not a failure, while matching two hosts' error strings would be the enumeration gap this module exists to close. A re-read that itself fails answers "still blocking", keeping the loud direction. A genuine failure — the review re-read and still holding — reds the run, since the PR is left exactly as deadlocked while every other signal says the cap was handled. Every outstanding block is attempted before anything is reported: a PR that drew findings on more than one round carries several reviews that all still block (neither host rewrites an earlier round's state when a later one posts), so aborting on the first refusal would leave the rest blocked while reporting one tidy failure. The transport arrives as a **thunk**, not a resolved value, because only the release knows whether a route is needed at all: the overwhelmingly common capped push has nothing outstanding, and resolving one there would re-list every changed file — and on Gitea re-fetch the whole unified diff — on every push for the rest of the PR's life to build a route it never calls. The filter runs first; the route is resolved only against a non-empty list, and a throwing thunk reds the run for the same reason a refused dismissal does. [LAW:carrying-cost] The dismissal message carries the same cap sentence the notice carries and states plainly that the findings were **not** re-checked; a dismissal that merely vanished would read as "the reviewer looked again and is satisfied". [LAW:no-silent-failure]

**A marker is trusted from the review's AUTHOR, and only then from its body.** On a public repo any account with read access can submit a `COMMENT` review, so a body ending in `REVIEW_MARKER` used to forge a review *round* — enough of them push a PR past its cap and it is never reviewed again, the strictly stronger sibling of forging a notice. `isOwnArtifact` (`src/transport.js`) is the ONE gate, applied once per review at the top of `summarizePriorReviews`' pass, before a body is read at all: it covers the round count, both cost tallies, the RA review-id set (which decides whose inline comments are ours and whose block may be dismissed), the notice's idempotency key, and the release-failure dedup. Covering one alone would be worse than covering none — it would make that field look protected while the rest stayed forgeable, an inconsistent trust model inside a single function. [LAW:single-enforcer] `parseAgentArtifact` is left answering only "what does this body say"; *who wrote it* is a separate question with a separate answer, which is what lets one gate serve every consumer. [LAW:decomposition]

The identity is parsed ONCE per run by `resolveReviewerIdentities`, over the **distinct tokens the run holds** — deduped in `run.js` where the token strings live, so an ordinary single-token run pays for exactly one probe. It is a SET rather than a single value because a PR outlives the configuration that reviewed it: setting `GITHUB_REVIEW_TOKEN` mid-flight (which the README recommends, to get formal approvals) makes the account posting round N+1 different from the one that posted round N, and a single-value identity disowned every earlier round — resetting count and cost, and, the serious half, dropping an outstanding `REQUEST_CHANGES` out of the set `releaseUnrevisitableBlocks` can release, which is the round-cap deadlock returning by the back door. The set covers what the run can prove: the tokens in its own hand. Rotating one PAT to a *different* PAT is not covered and is stated rather than papered over — there is no way to learn an identity the run no longer holds.

The two arms come from a **measurement** taken in a real Actions job (2026-08-24), because every cheaper discriminator is measured-wrong: `author_association` reads `NONE` for `github-actions[bot]`, byte-identical to an outside contributor, and `user.type === 'Bot'` *alone* reads a user-PAT's own reviews as not-ours, silently zeroing the round count and disabling a cost control — strictly worse than the forgery it set out to stop. `GET /user` answers `200` for a user PAT, which therefore names itself → exact login match. An installation token is **confirmed, never inferred**: it is recognized by `GET /installation/repositories` answering `200` (which a PAT answers `403`), not by the `/user` refusal, because `403` is not exclusive to `Resource not accessible by integration` — a secondary rate limit, SSO/SAML enforcement and some PAT scope failures all answer `403`, and reading any of them as "installation" would resolve a PAT onto the bot arm and zero its round count. Establishing the fact rather than deducing it from an absence is the whole difference; matching GitHub's error prose would be the same inference wearing a string compare. [FRAMING:representation]

The bot arm is **deliberately coarser** than the login arm and says so where it lives: it admits any `Bot`, so what it buys is not "this action's own installation" but "the forger must be a privileged app already installed on this repo" — a large reduction from *any account with read access*, not an elimination. It is not pinned to an account id because it cannot be: the same measurement found that an installation token cannot name its own app (`/app` and `/repos/{o}/{r}/installation` are JWT-only, no header carries one), and the only pinnable value — a hardcoded `github-actions[bot]` — would reject the own reviews of any consumer using `actions/create-github-app-token`, zeroing their round count. Pinning waits on a way to learn the app identity, not on someone deciding it would be nice. Host-agnostic by shape rather than by branch: Gitea serves `/user` for its own token, so a Gitea runner lands on the login arm with no host test. An identity that resolves to neither arm **throws**, and so does an empty set — "nothing is ours" reads exactly like a PR with no prior rounds, which is the zeroed cap again. [LAW:no-silent-failure] Resolution runs *after* the fork gate, so that gate still decides from the `pr` object alone and no API call in front of it can red a fork run.

## Build and release

```bash
npm install
npm run build          # ncc bundles src/index.js -> dist/index.js (+ licenses.txt)
```

- **`dist/` MUST be committed.** The Actions runner executes `dist/index.js` directly — it never runs `npm install` or a build step. Every change under `src/` requires `npm run build` and committing both `src/` and `dist/`.
- **`npm test`** runs the `node:test` suite in `test/`. Tests cover the exported pure functions across the `src/` modules (`config`, `diff`, `provider`, `selection`, `failover`, `review`, `transport`, `usage`, and the engine adapters) plus two collector smoke tests that perform a full MCP handshake against the self-respawned server: one spawning `dist/index.js --review-collector-server` (the bundled entry), one driving the actual `createReviewCollector` config from source (`src/collector.js --review-collector-server`). Both entries must work because `createReviewCollector` self-references `__filename` — the bundle in production, but `src/collector.js` when the engine is driven from source (tests, `scripts/local-review.js`). CI also asserts that committed `dist/` matches a fresh build (`npm run build` + `git diff --exit-code dist/`).
- Keep PRs to one fix/feature each, against `main`.

### Local review (dev diagnostic)

`scripts/local-review.js` (`npm run review:local`) runs a **faithful review locally** — the real multi-scope engine, the real prompts, the real MCP collector — against a real diff (`--mode pr`) or the working tree (`--mode repo`), with **no GitHub**. It drives the same `runMultiScope` production uses for **both** modes (the material is the only differential), so it is impossible to exercise one mode in production but not locally. It exists to answer "what does the engine actually do?": it reports, per engine spawn (the scout plus one worker per scope), whether the model **explored the repo** (`Read`/`Grep`/`Glob`) and which files it read beyond the changed set, plus the aggregated findings, summary, and summed cost. It reuses the action's own seams (`synthesizeProviderConfig`, `parseUnifiedDiff`, `buildPrMaterial`/`buildRepoMaterial`, `runMultiScope`, `renderRepoReport`), so its behavior matches a production run for the same inputs — it is an instrument, not a second implementation. The provider credential is read from the same env var the action uses (`DEEPSEEK_API_KEY`/`ZAI_API_KEY`/`OPENAI_API_KEY`); see `--help`. This is dev-only tooling (`scripts/`), outside the shipped surface — it does not bump the version.

### Cutting a release

Releases are git tags (`1.19.0`, no `v` prefix). Consumers pin the action by tag — the `dist/index.js` + `action.yml` at the tagged commit are what executes — and most pin the **moving tag `@v1`**, which always points at the latest release.

**This action ships only on the `v1` line.** Every release is a `1.x` version; `scripts/release.sh` refuses anything else (`[LAW:single-enforcer]`); `@v1` is the one moving tag consumers track. There is no `v2` and there will not be one — breaking changes are absorbed into the `1.x` line (see the level guidance below), so a consumer pinned to `@v1` always gets the latest without ever migrating a major.

**Every PR that changes what consumers run bumps the version, in that same PR.** The shipped surface is `src/`, `action.yml`, `review-agent/`, and the `dist/` built from them. A PR touching any of those edits `package.json`'s `version` by the correct semver level and rebuilds `dist/` — so `main`'s `package.json` is *always* the next publishable version, never lagging what's merged (the drift that left `package.json` at `0.1.0` while the tag was `0.1.1`). [LAW:one-source-of-truth] A PR that touches only docs, `scripts/`, or this file does **not** bump — bumping it would cut a release with no consumer-visible change.

Pick the level by what the diff does to the consumer contract:

- **patch** (`1.19.0 → 1.19.1`) — a bug fix or internal change; inputs and observable behavior are unchanged.
- **minor** (`1.19.0 → 1.20.0`) — any consumer-visible change: a backward-compatible addition (a new optional input) *or* a breaking one (a removed/renamed input, a changed default). The major component never moves past `1` — `release.sh` enforces it — so a break is still a minor bump on the `v1` line and `@v1` consumers receive it. Signal a break in the release notes, not the version's major.

Versioning is split into two parts, deliberately:

1. **Bump** = part of the change itself, not a separate release chore. In the same PR that changes the shipped surface, edit `package.json`'s `version` to the level above, run `npm run build`, commit `package.json` + `dist/`, and merge to `main` via a PR like any other.
2. **Publish** = `scripts/release.sh`, run on a clean, up-to-date `main`:

   ```bash
   git checkout main && git pull && ./scripts/release.sh
   ```

   It reads the version from `package.json` (the single source of truth), **refuses any version whose major is not `1`**, refuses to run if the committed `dist/` doesn't match a fresh build, then tags the commit, re-points `v1`, pushes the tags, and creates the GitHub Release with generated notes. It never edits or commits anything — the bump already happened in step 1.

- There are **no major version bumps.** `release.sh` rejects any non-`1.x` version (`[LAW:single-enforcer]`), so the project can never accidentally cut a `v2` (the way `2.0.0` was cut by mistake); `@v1` is the single moving tag, always pointing at the latest `1.x` release.

## Architecture

The source is split into focused modules under `src/` (orchestrator `run.js`; the config-file path `config.js` / `provider.js` / `selection.js` / `failover.js`; engine adapters under `engine/`; `prompt.js`, `transport.js`, `diff.js`, `review.js`, `collector.js`, `usage.js`, `report.js`, `dependency-diff.js`); `src/index.js` is the thin entry point that bundles to `dist/index.js`. It has **two entry points**, selected at the bottom (the `COLLECTOR_SERVER_ARG` check):

1. **Action orchestrator** (`run` in `src/run.js`) — the default mode the runner invokes.
2. **MCP collector server** (`runReviewCollectorServer` in `src/collector-server.js`) — the *same bundled binary* re-spawned as a stdio MCP subprocess by the engine. The MCP config (`createReviewCollector`) wires `command: node, args: [__filename, '--review-collector-server']`, so the binary is self-referential.

The central design seam is **judgment vs. transport**:

- **The engine owns review judgment.** Whichever engine runs (claude-code, codex, opencode) does so read-only — its only output channel is the MCP collector tools, so it cannot post to GitHub itself. For example claude-code runs in non-interactive print mode (`-p --output-format json`) with `Read`/`Grep`/`Glob` + the collector tools allowed and `Bash`/`Edit`/`Write`/`Web*` disallowed; each adapter enforces the equivalent read-only posture its own way (codex: read-only sandbox; opencode: `permission: {edit/bash/webfetch: deny}`).
- **The transport owns host I/O.** It reads the collector's records, validates them, and calls the review API of whichever host the runner reports.

This boundary is why findings — and the scout's scope plan, and per-module dependency judgments — flow through MCP tools rather than being parsed from the engine's prose: `request_change` (findings), `add_scope` (the scout's review scopes), `assess_dependency` (a worker's merge-risk judgment of a resolved `go.mod` bump, from which the host assembles the posted review's dependency section), and `finish_review` produce typed, schema-validated records (`records.jsonl`), and `readCollectedReview` enforces "exactly one `finish_review`" before anything reaches the host.

### Engine adapters and configuration

An engine is reached only through an **adapter** (`src/engine/{claude-code,codex,opencode}.js`), registered by name in `src/engine/registry.js` — the single enumeration of engines. claude-code and codex share one CLI lifecycle via `makeCliAdapter` (`src/engine/cli.js`): `createReviewCollector → materializeHome → runEngine spawn → readCollectedReview`, with nested `try/finally` owning home + collector teardown. Each adapter supplies only its spawn primitives (`materializeHome`/`buildCommand`/`assertSucceeded`/`extractUsage`/`classifyError`) and a `capabilities` declaration (`apiTypes`, `credentialKinds`, `reasoningEfforts`). [LAW:decomposition]

Those capability declarations are the **single source of truth for config validation** [LAW:single-enforcer] — both config paths derive from them, so an illegal combination is rejected identically whichever path it came through:

- **Simple mode** (no `CONFIG_FILE`): `src/provider.js` turns the `PROVIDER` value + its provider-specific inputs into one typed `ReviewConfig`. `PROVIDERS` is the one table of concrete providers (`codex`/`zai`/`deepseek`/`claude-subscription`), each row naming its engine, its endpoint **preset**, and its own credential input; `resolveEndpoint` turns that preset plus the row's inputs into the resolved endpoint, so a provider paid for differently is a row, not a branch. Each provider owning a distinct credential input is half the security invariant: `PROVIDER` alone picks the row, credential presence never steers it, so one provider's key can never be read into another's slot. `PROVIDER_ALIASES` (`auto → claude-subscription` since 1.42.0, `deepseek` before) is the one place to retarget every `PROVIDER: auto` consumer via a release, and `auto` is the default — a consumer that names no provider is retargeted centrally. The retarget is safe from one line precisely because a consumer missing the new target's credential fails at startup naming the input, before any spend, rather than falling back to a paid key that happens to be set. [LAW:no-silent-failure]
- **Config-file mode** (`.github/review-agents.yml` present): `src/config.js` parses, validates against the adapter capabilities, and resolves an ordered failover **chain** of `ReviewConfig` values; every `credentialEnv` in the chain must be set at startup; an endpoint is written as either the pinned `preset` form or the fully manual form. `src/selection.js` resolves the per-PR config name (label `review:<name>` > body trailer `Review-Config:` > `CONFIG` input > file `default`), failing loud on ambiguity or an unknown name.

`src/failover.js` (`produceReview`) is the single owner of retry timing and walks the chain: transient errors (classified at the adapter) retry ≤3× per config then advance; non-transient throw immediately (no failover); `buildAttributionFooter` names the config that actually produced the review. **The chain is walked exactly once**, so the ladder now has TWO bounds and ends at whichever fires first: a **count** (`PER_CONFIG_LIMIT × chain.length`) and the pre-existing **clock** (`budgetLeft === 0` on any transient catch, which an uncapped server `Retry-After` can reach well before the count does — often the tighter of the two at the 25-minute default). That count is `produceReview`'s OWN axis, not the whole ladder: each of its attempts is a full scout→workers pass whose every spawn retries 3× inside `retryTransientSpawn`, so the default one-config chain is **9 spawns and ~12–24s of backoff**, not 3 and ~5s. Tens of seconds is now the entire patience budget for a single-config deployment, which means a genuine 60s provider outage reds the run where the sweep would have absorbed it — deliberately: one re-run of a stateless reviewer that logged its true cause is cheaper than the incident below, and the lever for a flaky provider is a `fallback` config (the count scales with chain length), never a longer wait on the same one. The change is not that the clock stopped applying; it is that a count bound exists **at all**. Before, the clock was the *only* terminator, which is exactly why a provider failing in 500ms could consume the whole budget: with nothing counting, the run lasted precisely as long as it was allowed. There is deliberately no outer "sweep the chain again" loop: a second walk re-runs identical work (same config, endpoint, credential, prompt), and for the one-config chain that is the default (`PROVIDER: auto`) it is nothing but a multiplier on `PER_CONFIG_LIMIT` wearing a loop. [LAW:one-type-per-behavior] Its only real content — "let more time pass before retrying" — is what the per-config backoff already does. That duplicate axis is what made a spent subscription quota cost 25 minutes: the CLI answers every spawn in ~500ms with a structured `"error":"rate_limit"` event, which `TRANSIENT_RATE_LIMIT`'s `rate.?limit` alternative matches (its other alternative, `\b429\b`, is the genuinely different HTTP-429 backpressure case) and so classifies transient, and the ladder multiplied (3 spawn-level × 3 per-config × N sweeps) with nothing but the wall clock to stop it — the run lasted exactly as long as it was *allowed* (138 spawns), then reported the *deadline* as the cause, so the remedy on screen ("raise `TIME_BUDGET_MINUTES`") would have doubled the waste. [FRAMING:representation] The fix is the axis's removal, not a cap on it: a cap is the same behavior with a knob left to tune. A quota wall and a real 429 are **distinguishable** — the wall carries a structured `error` field and a reset time, an HTTP 429 carries a status code — but they are deliberately *not* separated at the classifier, because the incident yielded 135 samples of the wall and zero of a real 429, so any splitting predicate would be validated on one side only. Bounding by count needs no such discrimination, so walls never yet seen (a suspended account, a spent prepay balance) end on the same path. Typing the wall is a legitimate follow-up, gated on capturing a genuine 429 first. [LAW:no-silent-failure]

### The line-anchor invariant (most fragile part)

This section applies to **`pr` mode only** — `repo` mode has no diff and no anchors. A finding anchors to a **new-file line number**, defined **once** in `patchLines` (`src/diff.js`): each `@@` hunk header resets the new-side counter; only added (`+`) and context (` `) lines advance it and are anchorable (deletions have no new-side line). Three consumers derive from it and must never reimplement it:

- `annotatePatchWithLines` — labels each anchorable diff line `LINE N` in the prompt so the model cites the right line.
- `buildReviewAnchors` — the `path:line` set used by `partitionFindings` to reconcile each finding with the visible diff.
- `transport.toComment` — maps a finding's `line` to the host's comment anchor.

The two-way contract: the model is shown lines as `LINE N` and should comment on those. When it anchors slightly off (a line just outside the hunk), `partitionFindings` (`src/review.js`) does **not** abort the review — that would discard every valid finding and red the run for one model slip. Instead it reconciles each finding as a value: a line within `MAX_ANCHOR_SNAP_DISTANCE` of a reviewed line is snapped to that line (body annotated so the move is explicit); a line too far from any reviewed line becomes an *unanchored* finding that `submitReview` renders in the review summary and the PR sink (`runPrReview`, where `partitionFindings` is applied once to the merged multi-scope findings) logs as a warning. Either way the finding still counts toward the `REQUEST_CHANGES` verdict, so a mis-anchored real issue can never silently downgrade to APPROVE. [LAW:no-silent-failure]

### Host transport (GitHub + Gitea)

The action talks to whatever host the runner reports — the API base comes from `GITHUB_API_URL` (set by GitHub Actions and Gitea's `act_runner` alike), never hardcoded. The two host families differ in exactly four places, all behind one `transport` chosen once by **capability** in `selectTransport` (not by hostname):

- **Diff source.** GitHub's `listFiles` carries per-file `patch`; Gitea's does not. When no file has a `patch`, the transport fetches the unified `.diff` and `parseUnifiedDiff` splits it into the same `{filename, status, patch}` shape.
- **Comment anchor.** The same new-file line number becomes `{line, side: 'RIGHT'}` on GitHub and `{new_position}` on Gitea.
- **Approval verb.** `approveEvent` — GitHub's imperative `APPROVE` vs Gitea's past-tense `APPROVED`.
- **The dismissal route** (`dismissReview`) — GitHub `PUT .../dismissals`, Gitea `POST .../dismissals` with `priors: false` (`true` would sweep a human's earlier reviews). Measured against live instances; sending GitHub's verb to Gitea is a 405. The tests' fake serves exactly one host's row and 404s anything else, so a swapped route fails there.

**Dismissal is also the one call in this whole action that can need a THIRD credential.** `releaseUnrevisitableBlocks(octokit, resolveTransport, { ..., dismissOctokit = octokit })` (`src/transport.js`) takes an optional `dismissOctokit`, wired in `run.js` from `DISMISS_TOKEN`. It exists because Gitea's dismiss endpoint needs the dismissing account to hold repo-*Admin* — `GITHUB_REVIEW_TOKEN`'s `write` access, which is enough to *post* the review, 403s trying to *dismiss* it (measured against a live Gitea 1.27.1: itv.4/itv.4.1). GitHub needs no second credential — its dismissal already works at the review token's own access level — so `DISMISS_TOKEN` unset (the default, and every sane GitHub run) makes `dismissOctokit` fall back to `octokit` and nothing changes there. The input is deliberately **not** host-gated, and is not named as if it were: the dismissing identity is a value the caller carries, honored wherever it is set, because gating it on the host would resolve the transport thunk purely to choose a credential — the re-listing (and, on Gitea, whole-diff re-fetch) that thunk exists to avoid — and would put a host branch back inside the one function whose differences all ride on carried values. [LAW:dataflow-not-control-flow] It was `GITEA_DISMISS_TOKEN` for exactly one unreleased commit, and the name was the whole defect: it asserted a gate the code never had, in the one place no caveat can reach (PR #123). Every other call this action makes — reading the diff, posting the review, reading a review back to re-check state — stays on the ordinary review token; only this one write gets a wider identity, and only when a consumer opts in. [LAW:single-enforcer]

**Recognizing a live block is deliberately *not* a host difference.** `isOutstandingBlock` is one host-agnostic rule, because reading a review's state needs no knowledge of how the host serves diffs — and pairing the two would force a diff fetch just to ask a question about a review. Three spellings exist for one concept: the event *submitted* is `REQUEST_CHANGES` on **both** hosts, but the state *read back* is GitHub's `CHANGES_REQUESTED` and Gitea's `REQUEST_CHANGES`; and a dismissed review reports itself as state `DISMISSED` on GitHub while Gitea keeps `REQUEST_CHANGES` and flips a separate `dismissed` flag, so a state-only predicate re-dismisses the same Gitea review on every push forever. The union `BLOCKING_REVIEW_STATES.has(state) && !dismissed` is exact rather than lenient — the two read vocabularies do not collide, so each host's live spelling is accepted and each host's released shape rejected.

Everything downstream (`patchLines`, anchors, validation, the prompt) is host-agnostic. To support another host, add a transport instance — and, if that host recognizes a live block differently, extend the recognition rule beside `isOutstandingBlock`: `BLOCKING_REVIEW_STATES` for a new state spelling, and `reviewReleaseFacts` if it reports release under a key other than `dismissed`. Those two live together deliberately, so the recognition rule is one place rather than a spelling here and a field name inside the summarize loop — which is what let the loop's "reports, does not interpret" promise go stale.

The two omissions fail **differently**, and the difference is the useful part:

- A missing **state spelling** fails *silently*. That host's blocking reviews are never recognized as outstanding, so `releaseUnrevisitableBlocks` dismisses nothing and the round-cap deadlock quietly returns.
- A missing **release-flag name** fails *loudly and permanently*. An already-released review keeps reading as live, and since dismissal is not idempotent, every capped push re-attempts it, fails, and reds the run forever.

`announceUnreviewable` lives in `submitReview` and nowhere else. "It is reported on the PR and withholds approval" is a claim about a review being submitted, so any site that can fire it without submitting one makes it a lie. It was in `selectTransport` (also called to find a dismissal route) and then in `fetchFilteredFiles` (also called merely to *size* a diff for the budget/difficulty gradient, before the round-cap gate — so on any repo running `DAILY_BUDGET_USD`, every capped push warned about approval that was never at stake). Both placements were audits of callers, and the audit is what kept being wrong; hosting it at the sink makes it unreachable-by-construction from a path that submits nothing.

### Auth and environment

Each adapter translates the resolved `ReviewConfig` credential into the engine's own auth channel exactly once, in its `materializeHome`/`buildCommand`. **A resolved endpoint is three facts and no optional halves: `{apiType, baseUrl, credential: {kind, value}}`** — every endpoint has all of them, so there is no "subscription has no base URL" special case. **The security invariant lives in `PRESETS` (`src/provider.js`): an `oauth` credential is only reachable through a preset whose `baseUrl` is PINNED in code.** A row declares exactly one of `baseUrl` (pinned) or `defaultBaseUrl` (overridable), and `assertPresetsSafe` refuses at module load any oauth row that is overridable — so no input and no config file can point a long-lived subscription token at an arbitrary host, and reaching that state takes a reviewed code change rather than a typo. The config file mirrors this with two forms: **preset** (`preset` + `credentialEnv`, the only route to oauth) and **manual** (`apiType` + `baseUrl` + `credentialEnv`, always api-key because no field exists to say otherwise). Each engine declares the kinds it can translate (`capabilities.credentialKinds`), the single source both config paths validate against. The claude-code adapter maps the credential's KIND to an env fragment through `AUTH_ENV` — api-key → `ANTHROPIC_AUTH_TOKEN`/`ANTHROPIC_BASE_URL`, oauth → `CLAUDE_CODE_OAUTH_TOKEN` and *nothing else*. The fragments being disjoint is load-bearing: the CLI resolves `ANTHROPIC_AUTH_TOKEN` > `ANTHROPIC_API_KEY` > `CLAUDE_CODE_OAUTH_TOKEN` **silently**, so a run setting both would bill an API key while the operator believed the subscription paid. `--bare` must never be added to the flag list — it does not read `CLAUDE_CODE_OAUTH_TOKEN` at all. The adapter also writes a per-run temp `HOME` holding the bundled `review-agent/instructions.md` as the reviewer's user-global `~/.claude/CLAUDE.md`. codex writes the key to `CODEX_HOME/auth.json` + a `config.toml`; opencode writes `XDG_CONFIG_HOME/opencode/opencode.json` with `OPENCODE_DISABLE_PROJECT_CONFIG=1`. The per-run temp home and collector dir are created and torn down by the shared `makeCliAdapter` (`src/engine/cli.js`) nested `try/finally`, so cleanup runs even when the engine throws.

**Config isolation is a security boundary.** Each engine runs against an isolated config home, so the *reviewed repo* cannot hijack the engine's model, endpoint, credential, or MCP servers. codex/opencode pass an explicit env allowlist (never a `process.env` spread) so a prompt-injection payload in the diff cannot read `GITHUB_TOKEN` or other secrets via a shell expression. **Project instructions are isolated by working directory:** every engine discovers project instructions (`CLAUDE.md`/`AGENTS.md`/`opencode.json`) from its cwd — by walking *upward*, and (claude-code) by loading nested `CLAUDE.md` from subtrees *under* cwd when it reads files there — so the shared `makeCliAdapter` spawns each engine with cwd = a fresh **isolated scratch dir** (`fs.mkdtempSync(...)` in `src/engine/cli.js`) that is **not an ancestor of the reviewed repo**. That defeats both discovery paths: nothing is found upward, and the repo — read only by absolute path, never under cwd — never triggers nested-memory loading. (The cwd must NOT be the repo's *parent*: that would put the repo *under* cwd and re-open claude-code's nested-`CLAUDE.md`-on-read vector.) This closes the instruction-injection vector structurally for all engines at once, rather than via per-engine "disable project config" switches — none of which cleanly exists (claude-code's `--no-memory` also drops the reviewer's *own* instructions; codex has only a size knob; opencode's flag doesn't reliably cover project `AGENTS.md`). The repo is reached by its absolute path, named in the prompt via `REVIEWED_REPO_ROOT` (= `GITHUB_WORKSPACE`); Read/Grep/Glob access absolute paths outside cwd with no `--add-dir` grant. The reviewer's own instructions load from the isolated home (`HOME`/`CODEX_HOME`/`XDG_CONFIG_HOME`), keyed to env not cwd, so they are untouched. codex additionally passes `--skip-git-repo-check` because its scratch cwd is not a git repo (`codex exec` otherwise hangs waiting on stdin). A repo-committed instruction file stays *readable* as context (the agent may `Read` it) — it is simply no longer auto-loaded as binding directives. This is defense in depth behind the unconditional fork check (fork PRs are never reviewed), narrowing the residual same-repo-PR surface.

### Cost reporting

Every review reports its cost in the attribution footer of the PR review comment (and the run log). `runEngine` resolves with the engine's captured stdout; each adapter exposes a pure `extractUsage(output, config) → {inputTokens, outputTokens, cost}|null`.

**`cost` is discriminated by its BASIS — was this paid in dollars at all?** (`THE COST VALUE`, `src/usage.js`):

- `{basis:'dollars', usd}` — real spend. **The only arm any spend fold reads.**
- `{basis:'subscription', notionalUsd: number|null}` — plan quota. `notionalUsd` is Anthropic *list price* for tokens nobody was charged for: emitted everywhere a cost is, summed into nothing. `null` is the honest "billed to quota, list price not reported" — never a fabricated `0`.
- `{basis:'unpriced', reason:'no-price'|'not-reported'}` — dollars, figure unrecoverable.

**The spend exclusion is structural, not a rule.** The notional figure lives under a *different name* on a *different arm*, so a spend fold has no `usd` to read on a subscription cost and cannot pick it up by mistake. This runs all the way to the wire: a subscription review writes a differently-named marker (`agent-review-notional-usd`), so `parseCostMarker` — the one reader behind every spend fold (`sumCostToday`, `summarizePriorReviews`) — has literally nothing to match. One `usd` field plus "remember to check the basis first" would be a rule, and a rule gets forgotten exactly once, silently, inside a total. That is not hypothetical: before `zai-billing-xl0.2` (1.45.0), reviewing PR #113 reported `$63.59` of *notional* dollars as a PR spend total and fed them to the `DAILY_BUDGET_USD` gate. [LAW:types-are-the-program]

`costFromEnvelope` (`src/engine/claude-code.js`) resolves the basis ONCE, from `endpoint.credential.kind === 'oauth'` (`isSubscription`) — never from a hostname; `PRESETS` pins every oauth credential to Anthropic's own `baseUrl`, so a subscription run IS an Anthropic run by construction and `isAnthropicEndpoint` stays a plain whitelist with no special case. codex and opencode declare `credentialKinds: ['api-key']`, so neither adapter can reach the subscription arm at all. Each adapter declares its own unpriced reason at the point it knows it (codex or a foreign-endpoint claude-code run: model absent from the price table — `no-price`; a genuine Anthropic run that omitted `total_cost_usd` — `not-reported`), so the orchestrator never re-derives why cost is missing.

Usage is carried as a value from each adapter's `produceReview`, summed across the scout + worker spawns by `sumUsage` (`src/multiscope.js`) — which delegates to `sumCost`, **the one owner of the "never add across bases" rule**: a dollar of spend and a notional list-price dollar are different units, so a mixed sum resolves to `unpriced` rather than a blend, and a partly-unreported notional is wholly unreported rather than a partial total passed off as complete. Because every spawn in a pass runs on one config the basis is uniform there; across a PR's *rounds* it is not, which is why `summarizePriorReviews` keeps two tallies of one shape (`emptyTallies`/`tallyCost`) and the footer renders them side by side — `PR total …` and `PR list-price total …` — never added. [LAW:dataflow-not-control-flow]

Cost is **one mechanism — tokens × the price table — for every priced provider** [LAW:one-type-per-behavior], with a single exception. `PRICES_PER_MILLION` in `src/usage.js` is the one table, keyed by the exact model id each engine reports (`gpt-*`, `deepseek-*`, `glm-*` — namespaces don't collide); `computeCostUsd` prices a run from it. Each adapter buckets its own raw usage into the table's shape (codex: `cached_input_tokens` billed at the cached rate; claude-code: `cache_read` at the cached rate, fresh + `cache_creation` at the full rate). The table is a representation that drifts from each vendor's real prices and has **no machine source — it must be updated by hand**; each entry carries a dated source URL (verify before trusting old figures). [LAW:one-source-of-truth] The single exception is a **genuine Anthropic** claude-code run (`isAnthropicEndpoint`): there Claude Code's own `total_cost_usd` is the cost, since it is already Anthropic-priced. An oauth run reads that same figure but tags it `basis:'subscription'` — same source, never recomputed, but carried as `notionalUsd` so no spend fold can reach it (see above). The wrong-vendor trap this avoids: Claude Code computes `total_cost_usd` against *Anthropic's* table, so on an Anthropic-**compatible** endpoint (z.ai, deepseek) that figure is the wrong vendor's — `costFromEnvelope` discards it and prices from the provider's own table entry instead. The Anthropic check is a whitelist (apex or true `.anthropic.com` subdomain), not a per-vendor blacklist, so a lookalike host or a future compatible endpoint can never be wrongly trusted. A model with no table entry renders cost as `unknown` (tokens still shown) and logs a warning naming the model to add; missing usage omits the cost line loudly, never silently. [LAW:no-silent-failure] Every rendered cost is an **estimate** (`est.`) — table × tokens, or Claude Code's client-side `total_cost_usd` — never a billed charge.

### Session transcript

Every review run captures the **full session** of every engine attempt for inspection — capture is unconditional, with no opt-in flag. [LAW:no-mode-explosion] It lives in `runEngine` (`src/engine/run.js`), the one place that owns the child's raw streams: its `finish()` helper runs on *every* termination path (success, non-zero exit, spawn error, timeout), so a transcript is produced for every attempt, including a failed one. The transcript is the engine's own raw streams **verbatim** — prompt (delivered on stdin) + raw stdout + stderr — never a reconstructed narrative. [LAW:one-source-of-truth] The API key is never an input to `buildTranscript` (`src/debug.js`), so it cannot leak into a surfaced transcript.

For claude-code, `buildCommand` always uses `--verbose --output-format stream-json` (one canonical format, no flag), so the stream carries every thinking/tool-use event. [LAW:one-type-per-behavior] `parseResultEnvelope` (`src/engine/claude-code.js`) normalizes the terminal `result` event back to the same envelope the plain `json` form produced, so `assertSucceeded`/`extractUsage` stay uniform. [LAW:dataflow-not-control-flow] codex (`exec --json`) and opencode (`run --format json`) already stream full reasoning + tool calls. The surfacing is an effect at the boundary (`emitTranscript`): a collapsible `::group::` in the Actions log **and** a file under `$RUNNER_TEMP/agent-review-transcripts/`, exposed via the `transcript-dir` action output (set once at the start of `run()`, so an `if: always()` `actions/upload-artifact` step has the path on every termination path, including a fork-skip with no engine spawned). A log/write failure warns but never aborts the review. [LAW:no-silent-failure]

### Approval permissions

The default `GITHUB_TOKEN` cannot approve PRs. With no `GITHUB_REVIEW_TOKEN`, a clean review still posts a review — a `COMMENT` one whose body reads `✅ Approved` (`reviewEvent` in `src/transport.js`), so the visible result lands either way; only the formal `APPROVE` state is withheld. Findings still submit a `REQUEST_CHANGES` review. Set `GITHUB_REVIEW_TOKEN` (used for *all* GitHub calls when present) to submit formal approvals.

## Two CLAUDE.md files — do not confuse them

- **This file** (`/CLAUDE.md`) — guidance for working *on* this repo.
- **`review-agent/instructions.md`** — a runtime artifact: the reviewer's instructions, copied by each adapter's `materializeHome` into the spawned reviewer's engine-global instructions file (`~/.claude/CLAUDE.md` for claude-code, `AGENTS.md` for codex/opencode). Editing it changes *how reviews are conducted*, not how you develop here. The review task prompt itself (the law priorities, the `request_change` rules) is the big template literal in `buildReviewInput`.
